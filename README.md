# django-aicore

Переиспользуемое Django-приложение — общий AI-слой проекта. Вы выносите из своих
приложений всё, что связано с обращением к LLM, и настраиваете это в одном месте
через веб-интерфейс, не трогая код.

Зачем оно обычно нужно:

- **Смена моделей без деплоя.** Провайдеры настраиваются в UI: endpoint, ключ,
  модель, роль. Код просит «умную модель для анализа» или «дешёвую для разметки» —
  какую именно модель за этим стоит, решает владелец проекта в настройках.
  Модель подорожала или оглупела — меняется в два клика, код не трогается.
- **Роли и фолбэки.** Провайдеры делятся по ролям (`smart`, `cheap`, `vision`,
  `embed`, …) с цепочками фолбэков; несколько активных провайдеров одной роли —
  норма, побеждает приоритет.
- **Пул прокси с ротацией.** Запросы идут через самый надёжный активный прокси;
  упавший транспорт ретраится через другой, счётчики успехов/сбоев видны в UI.
- **Фоновые задачи с готовым фронтом.** Длинные AI-вызовы уходят в тред и
  поллингуются с сервера — не упираются в таймаут gunicorn. JS-слой
  (`startAndPoll`, блоки ошибки/успеха, возобновление оборванного опроса)
  прикладывается, писать свой не надо.
- **Прозрачность вызовов.** Каждый вызов пишет в журнал модель, токены, цену,
  использованный прокси и полный промпт; фронт показывает пользователю «что
  отправлено» и сырой ответ модели прямо на странице.
- **Реестр задач.** Температура и выбор провайдера под конкретную задачу
  переопределяются из UI по стабильному ключу задачи — подбор модели становится
  эксплуатацией, а не правкой кода.

Работает с любым OpenAI-совместимым API, а также с нативным Gemini и OpenRouter
(диалект задаётся у провайдера). Django >= 4.2, Python >= 3.10.

## Установка

```bash
pip install git+https://github.com/geweb7/django-aicore.git
```

Подключение в `settings.py`:

```python
INSTALLED_APPS += ["django_aicore"]
```

URLs:

```python
urlpatterns = [
    ...
    path("ai/", include("django_aicore.urls")),
]
```

Миграции:

```bash
python manage.py migrate
```

Примечание: Python-пакет называется `django_aicore`, но ярлык приложения и
namespace URL остаются `"aicore"` (`reverse("aicore:tasks")`,
`{% url "aicore:providers" %}`), а таблицы в БД — `aicore_*`. Это сознательно:
проекты, ранее использовавшие приложение под именем `aicore`, переключаются на
пакет без переименования таблиц и без переноса данных.

После этого настроить провайдеров: `http://ваш-хост/ai/providers/`
(или через Django Admin — модели там тоже зарегистрированы).

## Что внутри

| страница | что настраивается |
|---|---|
| `/ai/providers/` | провайдеры: endpoint, ключ, роль, теги, приоритет, диалект |
| `/ai/tasks/` | реестр задач: тег, роль, temperature — без правки кода |
| `/ai/proxies/` | пул прокси со счётчиками успехов/сбоев |
| `/ai/calls/` | журнал всех вызовов: исход, фаза отказа, токены, цена |

Все страницы требуют логина (`login_required`).

## Синхронный вызов AI

```python
from django_aicore.core import call_task, parse_json

content, usage = call_task(
    "myapp.session.step1",              # стабильный ключ задачи
    messages,
    name="Шаг 1 (заметки)",             # подпись для UI
    role="smart", temperature=0.0,      # дефолты регистрации — «что просит код»
)
data = parse_json(content, usage)
```

Провайдера и температуру выбирает **слой**, а не вызывающий код: задача при первом
вызове сама регистрируется в реестре, дальше пользователь правит её настройки в
`/ai/tasks/` — тег, роль, temperature — не трогая код.

**Ключ — стабильный слаг, не подпись.** `name` меняйте свободно; `key` — никогда:
переименование перерегистрирует задачу с дефолтами из кода, и настройки пользователя
молча перестанут применяться. Первый сегмент ключа — имя приложения
(`myapp.session.step1`): по нему слой определяет приложение для `X-Title` в OpenRouter.

Разрешение провайдера: тег задачи среди активных провайдеров (по `priority`) → нет
тега или нет такого активного → роль (с цепочкой фолбэков).

Роли: `smart`, `cheap`, `smart-alt`, `genius`, `vision`, `embed`. Фолбэк `cheap`,
`smart-alt`, `genius` → `smart`. У `vision` фолбэка **нет** намеренно: на текстовой
модели vision-вызов молча не сработает, поэтому лучше падение. Нет подходящего
провайдера — `AIUnavailableError`.

Несколько активных провайдеров с одной ролью — нормальное состояние: кто победит при
выборе по роли, решает `priority` (меньше — раньше), он виден в списке и уникален.

Диалект провайдера задаёт формат общения:

- `openai` — POST ровно на указанный `base_url`, путь не достраивается;
- `gemini` — своё тело запроса, путь и модель дописываются к базе;
- `openrouter` — свои заголовки, адрес зашит в коде.

`messages` — канонический OpenAI-формат для **всех** провайдеров (для gemini
конвертируется внутри). `content` элемента может быть строкой или списком частей
(`{"type": "text"}` / `{"type": "image_url"}`); картинки передаются как base64 data URI,
конвертацию под конкретный API слой делает сам.

### `usage` — факты каждого вызова

Показывать пользователю отправленный промпт и модель обязан каждый AI-блок. Слой
кладёт факты в `usage`:

| ключ | что это |
|---|---|
| `sent` | что ушло в модель, готовый к показу текст |
| `model` | какая модель фактически обслужила вызов |
| `role` | роль выбранного провайдера |
| `tag` | тег, которым сделан выбор (пусто — выбирали по роли) |
| `temperature` | фактическая температура вызова |
| `upstream` | хостер, которому OpenRouter отдал запрос |
| `retries` | сколько прокси пришлось перебрать (0 — прошёл с первого) |
| `tool_calls` | вызовы инструментов, если модель ответила ими (формат OpenAI) |
| `cost` | цена вызова в долларах, как её назвал провайдер (сейчас только OpenRouter) |
| `call_log_id` | id строки этого вызова в журнале |

`AIUnavailableError` несёт тот же `usage` — при ошибке видеть отправленное нужнее всего:

```python
except AIUnavailableError as e:
    show(e.usage.get("sent", ""))
```

### Нативные вызовы инструментов — `tool_calls`

Отправку инструментов делает приложение: `tools` кладётся в `extra_payload` и доходит
до запроса нетронутым. Возврат результатов — обычные сообщения
`{"role": "tool", "tool_call_id": …}`. Слой не исполняет инструменты, только доносит
вызовы наверх.

| ситуация | что вернётся |
|---|---|
| `tools` передавали, модель ответила вызовами | `content` = `""` (или текст), вызовы в `usage["tool_calls"]` |
| `tools` **не** передавали, модель ответила вызовами | `AIUnavailableError` с именами вызовов и сырым ответом |
| модель ответила текстом | как обычно; ключа `tool_calls` в `usage` нет |

Формат вызовов один для всех провайдеров — OpenAI; Gemini отвечает `functionCall`,
слой приводит его к тому же виду.

### `parse_json(text, usage)` — второй аргумент отдавать всегда

Без него сообщение о неудачном разборе теряет `finish_reason`, число токенов и модель.
Оборванный ответ отличается от битого синтаксиса всегда: если текст не заканчивается на
`}` или `]`, сообщение прямо говорит, что ответ обрублен, и причину надо искать в лимите
вывода или транспорте. При провале парсинга текст ответа вешается на исключение
(`err.raw`).

## Эмбеддинги

```python
from django_aicore.core import get_embeddings_batch, cosine_similarity

vectors, error = get_embeddings_batch(texts, caller="myapp: пересчёт графа")
```

Возвращает `(список векторов, текст ошибки | None)` — исключений не бросает, ошибку
отдаёт второй половиной пары, **её обязательно проверять**. Провайдер берётся по роли
`embed`, фолбэка нет: не настроен — это ошибка. Тексты бьются на батчи по `batch_size`
(по умолчанию 100), каждый батч — отдельная строка в журнале.

## Журнал вызовов

Каждый вызов `call_task` и каждый батч эмбеддингов пишут строку в `AICallLog` —
и успешный тоже. В строке лежит то, чего в тексте ошибки не видно: `upstream`
(хостер OpenRouter), использованный прокси, `error_kind` (фаза отказа: `proxy`,
`connect_timeout`, `read_timeout`, `connection`, `http`, `bad_json`, `empty_body`,
`provider_unavailable`, `upstream_error`), HTTP-статус, `finish_reason`, токены,
длительность, цена и `gen_id`.

На странице журнала — фильтры по исходу, фазе отказа, хостеру, модели и задаче, сумма
цены по отфильтрованному и кнопка «Обновить цены» (дозапрос цены у OpenRouter по
`gen_id` для строк, где её не было в теле ответа; не больше 200 строк за нажатие).

Журнал не глотает своих ошибок: **не записался — вызов падает**. В ветке ошибки сбой
записи не стирает саму ошибку AI — наружу уходят обе.

## Фоновая задача

Всё, что дольше пары секунд, стоит пускать так: длинная AI-цепочка в одном HTTP-запросе
рискует упереться в таймаут сервера. Цепочку из нескольких вызовов бить на фазы —
отдельная задача на фазу.

Сервер:

```python
from django_aicore.views import run_async

def start_analysis(request):
    task_id, poll_url = run_async(lambda: do_work(request.user))
    return JsonResponse({"poll_url": poll_url})
```

Фронт (jQuery подключается инклюдом слоя):

```js
startAndPoll(startUrl, postData, function (result) { ... }, function (msg, raw) { ... });
```

Формат задачи (он же ответ poll-эндпоинта) единый:
`{status, result, error, raw_response, usage, traceback}`, где `status ∈ {running, done,
error}`. Задача живёт в треде-демоне, состояние — JSON-файл во временной директории:
она **не переживает рестарт воркера**, после рестарта poll отдаёт 404 `{status: "unknown"}`.

### Дедуп повторного запуска

Долгие задачи нельзя запускать дважды параллельно — передайте `dedup_key`:

```python
task_id, poll_url = run_async(task, dedup_key=f"myapp:update_tips:{pk}")
```

Пока задача с этим ключом идёт, второй `run_async` с тем же ключом не создаёт новую —
возвращает `(task_id, poll_url)` уже идущей. Ключ снимается по завершении. Атомарность —
`cache.add`, работает в пределах общего бэкенда кэша.

### Ошибки фоновой задачи

У неожиданного исключения `error` получает тип (`ValueError: …` вместо голого текста),
а `traceback` — полный стек. У своей ошибки слоя (`AIUnavailableError`) тип не
приклеивается: её сообщение уже написано для человека. Туда же кладётся `usage`
упавшего вызова.

## Подключение фронта

```django
{% include "django_aicore/scripts.html" %}   {# в base.html приложения #}
```

Даёт jQuery и `django_aicore/js/tasks.js`: глобальные `netErrMsg`, `errorBlockHtml`,
`successBlockHtml`, `xhrErrorBlock`, `resumeErrorBlock`, `usageLine`, `pollTask`,
`startAndPoll`.

`usageLine(usage)` собирает из `usage` одну строку — модель, температуру, токены,
хостера, перебор прокси, время. Отдаёт **текст**, не HTML: вставлять через `.text()`.

### Блоки вызова

```js
$slot.html(errorBlockHtml(msg, raw, usage));           // вызов упал
$slot.html(successBlockHtml('Шаг 1', raw, usage));     // вызов удался
```

Блок сам рисует: подпись, строку фактов (`usageLine`), коллапс «что отправлено»
(`usage.sent`) и коллапс «сырой ответ» (`raw`). Тексты вставляются `.text()`-ом —
разметка из промпта или ответа модели читается буквами, а не исполняется.

При обрыве опроса (смена сети, разрыв через прокси) `onFail` получает третий аргумент —
`resume`, замыкание, возобновляющее опрос той же задачи:

```js
startAndPoll(startUrl, postData, onDone, function (msg, raw, resume) {
    $btnStart.prop('disabled', false).text('Анализ');
    $slot.empty().append(resumeErrorBlock(msg, raw, resume, function () {
        $btnStart.prop('disabled', true).text('Анализирую…');
    }));
});
```

`resume` приходит только там, где задача может быть жива (обрыв связи, 502/504). Его
нет, когда задача честно упала на сервере, истёк CSRF (403) или файл задачи пропал (404).
Автоматического ретрая нет: ошибка показывается всегда, возобновление — только руками
пользователя.

Четвёртый аргумент `onFail` — `usage` упавшего вызова, пятый у `resumeErrorBlock` —
необязательный колбэк перед возобновлением.

### Кастомизация вида

У каждого узла две метки: класс `aicore-*` — зацепка для CSS, `data-aicore` — для JS.

| узел | класс | `data-aicore` |
|---|---|---|
| обёртка | `aicore-err` / `aicore-success` | `err-block` / `success-block` |
| кнопка коллапса | `aicore-block__btn` | `sent-btn` / `raw-btn` |
| строка фактов | `aicore-block__facts` | `facts` |
| текст коллапса | `aicore-block__pre` | `sent-pre` / `raw-pre` |

```css
.aicore-block__pre { max-height: 500px; font-family: monospace; }   /* в CSS приложения */
```

Своего CSS слой не везёт: вид блока собран утилитами Bootstrap 5, инлайн-стилем задан
только `max-height` коллапса. Всё переопределяется обычным CSS без `!important`.
Раскрытие — на `data-bs-toggle` Bootstrap; нужно своё поведение — снимите атрибут у
`[data-aicore="raw-btn"]` и повесьте свой обработчик.

## Ретрай транспорта

Если запрос **не дошёл** по вине тракта (фазы `proxy`, `connect_timeout`, `connection`),
`post_json` повторяет его **через другой прокси**. Число дополнительных попыток —
константа `PROXY_RETRIES` в `django_aicore/core.py`; `0` выключает ретрай совсем.
Упавший прокси исключается из выбора на время этого запроса.

Не повторяется ничего другого: ответ, который дошёл (HTTP-ошибка, кривой JSON, отказ
хостера), и молчание модели после установленного соединения (`read_timeout`) падают с
первого раза — повтор оплатил бы те же токены дважды.

Каждая неудачная попытка двигает счётчик сбоев своего прокси, удавшийся со второй
попытки вызов приносит `usage["retries"] > 0`, а если провалились все — в сообщении
лежат все попытки: через какой прокси шли и на какой фазе оборвались.
